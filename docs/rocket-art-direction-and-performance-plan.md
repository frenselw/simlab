# 火箭模擬：卡通美術細節與性能優化方案

日期：2026-10-25。狀態：**P28已實作主方案；第1節為修改前診斷，第5節為驗收預算，實測與部署證據見第8節及活動計劃P28。真手機／真Moodle驗收另列。**

範圍屬於[火箭活動計劃](../plans/40-rocket-space-mission-lab.md)；沿用[共同風格](../plans/00-shared-platform-and-style.md)及[製作契約](simulation-scorm-production-guide.md)。手機控制面板修正是P27已另行實作的工作；本文件保留設計取捨，並記錄本輪美術實作。

## 1. 目標與現況診斷

視覺方向是「有細節的科普卡通模型」：辨識清楚的大陸輪廓、柔和但有層次的色塊、少量手繪質感、立體而乾淨的火箭。遠看輪廓清楚，中距離看得到海灣／山脈／雲帶，近看發射場有道路和材質。細節不能蓋住火箭、軌道與數字。

已讀取scene-art.js、scene.js、main.js，並檢視現有手機操作艙及地球全景截圖。具體問題：

| 現況 | 原因 | 優先修正 |
|---|---|---|
| 大陸像剪紙多邊形 | dayMap雖是4096×2048，但大陸由少量座標以lineTo直線相接 | 改進輪廓資料和輪廓設計，保留彎曲、海灣、半島及島群 |
| 發射場海岸近乎直線 | coast(z) = -11400 - 0.616z + 150sin(z/12000)，240km範圍內彎曲幅度很小 | 為本區設計連續海灣、岬角、河口；全球和局部共用地理來源 |
| 陸地像大色塊拼貼 | 沙漠／森林以少量橢圓填色，山脈為重複三角形，河流為粗折線 | 改成有方向和分支的色帶、山脊和水系，控制微細紋理對比 |
| 雲朵重複、海洋單調 | weather為28組重複橢圓；海面主要單色 | 畫2–3種雲帶結構，海洋使用淺灘到深海的克制漸層 |
| 太空空而平 | 900個星點雖有顏色差異，但大小和分佈接近均勻；背景只是漸層 | 改善星等、疏密與遠近感，加入極淡、固定的星野背景 |
| 性能預算容易被誤判 | ZIP很小，但Canvas生成的大貼圖上傳GPU後仍佔大幅記憶體 | 分開量度下載大小、CPU生成時間、GPU貼圖估算和實際幀時間 |

已有可保留基礎：單renderer、本地Three.js、快取貼圖、InstancedMesh樹木／建築、距離隱藏細節、有限DPR、低面數球體、薄大氣圈、暫停及背景頁面處理。沒有必要更換引擎。

## 2. 可行途徑與選擇

| 途徑 | 可得到的效果 | 成本與限制 | 決定 |
|---|---|---|---|
| 在現有Canvas直接手繪更多曲線 | 快速改善局部海灣、雲、材質 | 世界輪廓難長期手工維護；單純平滑現有頂點仍缺真實形狀 | 用於局部風格設計與小材質 |
| 簡化地理向量＋手繪配色，預先烘焙成貼圖 | 大陸可辨認又保持卡通；細節增加而逐幀成本接近原來 | 需一次離線整理資料、處理接縫與局部對齊 | **主方案** |
| 插畫師／AI製作風格稿，再整理成無縫貼圖 | 可快速試配色、筆觸、雲形和視覺方向 | 原稿通常不保證經緯度、接縫和地理一致性 | 可選風格參考，不作直接覆蓋地球的最終原圖 |
| 衛星照片、密集真實地形或重型後製 | 寫實效果強 | 不符合卡通方向；增加素材、像素與GPU成本 | 不採用 |

全球輪廓以Natural Earth 1:50m land／coastline為起點；其海岸資料包含主要島嶼，且是已簡化版本。[資料說明](https://www.naturalearthdata.com/downloads/50m-physical-vectors/50m-coastline/)。其地圖資料屬public domain，可修改及隨SCORM封裝分發；仍記錄版本、來源及處理方式，方便重建。[使用條款](https://www.naturalearthdata.com/about/terms-of-use/)。這是示意地球，沒有必要在畫面加國界、城市標籤或追求測繪精度。

## 3. 地球與發射區的具體製作方法

### 3.1 同一份地理，三個觀看尺度

1. **全球輪廓**：離線讀取land polygons、主要島嶼／湖泊，跨±180°經線先拆分／包邊，保存孔洞及南極封口。按輸出像素容許約0.5–1px輪廓誤差簡化，保留海灣、半島、島鏈；小於1px的細節省略或美術誇張，避免閃爍。不要把全部邊緣平滑成圓形。
2. **中距離地貌**：在陸地mask內繪森林、草地、荒漠及高山四種主要色域；邊界沿地形延伸，避免橢圓斑塊。山脊用兩側明暗與小面積雪頂，河流有粗細變化、支流及河口，淺海色帶跟隨海岸。
3. **發射區**：以同一全球底圖裁出現有240km區域。局部美術可新增約3–5個主要彎曲、少量次級海灣、河口沙洲和近岸島；細節只在區域內部補充，外圍保持與全球圖一致。發射台、河道、道路、近岸樹木共同使用此區域的座標／mask，避免換一張圖後樹長在海裡。
4. **近景**：沿用實例化樹木、庫房和山丘，在鏡頭能看見時才顯示。必要的近地細節用一張小型可重複材質及既有幾何；遠處一律回到烘焙圖。

現有shader在chart／經緯度之間有固定旋轉和發射位置轉換。先建立座標對照測試，將發射點、河口、海灣、山脊至少四個landmark對齊，才換素材。不得讓全球與局部各自畫一套地理，再只靠大範圍淡化遮掩錯位。

低空到軌道繼續使用同一球面。既有20–60km道具淡出只控制地上幾何，海岸／河流位置不能隨高度切換。全球／局部貼圖的混合取決於地表座標；測試相同地表點在不同高度和角度仍一致。沿用現有純視覺自轉約定，不藉美術修改物理座標或初速度。

### 3.2 配色和質感

- 海洋：深藍青主色、沿岸較亮的青色淺灘；只在局部放少量柔和波紋，避免全海面高頻噪點。
- 陸地：暖綠草地、偏深的森林、低飽和沙色荒漠；同一地貌用2–3階色值，保留大片呼吸空間。
- 紋理：繪畫紙感／短筆觸以低對比烘焙進色圖；以實際手機尺寸判斷能否看見，不以4K原圖放大觀感作驗收。
- 光照：保留球體明暗與柔和日夜交界，固定光源方向一致。避免把高對比定向陰影全畫死在色圖，以免與3D光照相反。
- 不加巨型卡通輪廓線、不加國界格線；可讀性由形狀、色層與光照建立。

### 3.3 雲和大氣

雲圖重畫為寬雲帶、碎積雲群和一兩個低對比旋渦區，保留大陸可見面積，避免同一朵橢圓重複。維持一個透明薄球殼；雲的暗部可畫入同一貼圖，首版不另加陰影投射層。動畫只小幅改uniform／旋轉，不重新畫Canvas；暫停與prefers-reduced-motion時靜止。

大氣保留現有Fresnel邊緣shader，調整厚度、日照側顏色和透明度；先做到乾淨的細藍邊及近地淡霧。透明全屏疊層是像素成本，不能只看三角形數量。

## 4. 太空、火箭與發射場

| 元素 | 美術方法 | 性能做法 |
|---|---|---|
| 星野 | 多數暗小星，少數較亮主星；白、微藍、微暖三色；疏密不均但不搶軌道線 | 沿用單個Points，增加size／brightness attribute；約700–1200點，保留地球遮擋 |
| 太空背景 | 深藍黑微漸層＋非常淡的斜向星帶，沒有濃彩霓虹星雲 | 一張約512px級預烘焙背景；按方向取樣，避免拖鏡頭時像貼在螢幕上；沿用上升淡入 |
| 火箭 | 保留可愛臉、圓潤輪廓；統一接縫、色帶、編號、金屬暗部 | 先修現有atlas；接縫／鉚釘遠看藏起，不為每粒細節加mesh |
| 發射台 | 淺色混凝土、暖黃導引線、深色排焰槽，少量邊緣磨損 | 接觸陰影沿用烘焙貼片；重複物件用既有InstancedMesh |
| 火焰／分離／RCS | 火焰有白芯與彩色外焰，輪廓自然；分離和RCS沿用已有正確事件 | 先改現有幾何與透明度，不新增模擬器；若日後加煙，限量池化並只在近地顯示 |
| 教學疊圖 | 地球最亮處仍能分辨軌道、速度／推力箭頭及節點 | 保持原位置、命中區、語義顏色；不加會覆蓋文字的glow |

## 5. 素材流程與性能預算

### 5.1 素材離線製作

新增一個專用離線製作腳本／小型素材來源目錄，產出本地WebP／PNG。向量解析、隨機筆觸、海岸距離色帶等只在製作時運行；runtime只讀圖片和更新少量uniform。固定seed，輸出可重建，保存來源授權和版本。

手機以2048×1024全球圖起步，桌面可用4096×2048；局部2048×2048先保留，避免窄河流過早消失。雲1024×512，其他小材質沿用256–512px。只載入選用的一組全球尺寸，切換場景共用texture；載入失敗沿用既有render-fault流程，不破壞可提交紀錄。

每份runtime素材加入活動manifest，SCORM包離線可開；控制高／低版本合計ZIP大小。這個方案不需要新runtime依賴。先用現有工具生成圖片；只有實測證明傳統貼圖無法達到記憶體預算，才評估KTX2與其decoder成本。

### 5.2 清楚區分三種成本

一般RGBA8貼圖連mipmap可按寬×高×4×4/3估算GPU用量；壓縮圖片的下載大小不能直接代表GPU佔用。[Three.js貼圖說明](https://threejs.org/manual/pages/textures.html)。

| 貼圖 | 現況估算 | 主方案手機估算 |
|---|---:|---:|
| 全球色圖 | 4096×2048：約42.7MiB | 2048×1024：約10.7MiB |
| 局部色圖 | 2048×2048：約21.3MiB | 保留：約21.3MiB |
| 雲圖 | 1024×512：約2.7MiB | 保留：約2.7MiB |
| 三者合計 | 約66.7MiB | 約34.7MiB |

以上未含火箭、地面小材質、framebuffer、MSAA、驅動開銷和CPU圖片／Canvas副本；只用於對比預算，並非已量到的完整GPU記憶體。重點是用更好畫法及選對貼圖尺寸增加可見細節，不盲目再加8K圖。

| 指標 | 預算／驗收目標 |
|---|---|
| 畫面複雜度 | 每幀≤100 draw calls、≤100k三角形，沿用現有硬上限；星野約1 call，地球／雲／大氣總計約3 calls |
| 手機貼圖 | 可列舉紋理連mipmap估算≤48MiB；全畫面記憶體另外記錄 |
| 桌面貼圖 | 可列舉紋理估算≤96MiB；仍只載入一套全球圖 |
| DPR | 手機上限1.5、桌面2；畫質降級可降至1.25／1，文字HTML不跟著變模糊 |
| 手機流暢度 | 指定中階真機持續≥30fps；記錄p50／p95 frame interval，目標p95≤33.3ms；兩項都看，不能只報平均fps |
| 操作回應 | 點按到畫面回應目標≤100ms；冷載首次可操作≤5s，記錄裝置、網路與快取狀態 |
| 包大小 | 最終SCORM ZIP≤5MB，素材從包內讀取，無CDN請求 |
| 相對回退限制 | 同機同路徑的p95若較本輪前基準變差>10%，先降裝飾成本再交付；此為守門目標，實測後評估 |

### 5.3 每幀工作與降級順序

1. 先量度scene.draw、HUD更新、positionTargets及物理各佔多少時間；現有animate在暫停時仍會每幀更新互動目標，值得量測，但不能未量度就認定是瓶頸。
2. 若確認多餘：將模型／鏡頭／尺寸改變合併為一幀重畫，暫停無互動時停止不必要的GPU繪製及DOM定位；拖曳、鍵盤、resize和context restore必須仍即時更新。
3. 畫質先降DPR，其次取消裝飾閃爍／粒子，再降低雲與大氣疊色，再隱藏遠處小道具。海岸形狀、軌道／箭頭、命中區、主字級和物理精度不降級。
4. 如需自適應，使用一段持續慢幀才降級，至少數秒冷卻，避免畫質上下跳；頁面背景、使用者暫停和首次貼圖上傳不算進穩態評分。不在每幀重新分配texture或粒子物件。
5. 共享貼圖按場景生命週期重用，替換時清理幾何／材質／texture；context restore重建後不能重播分離或偷偷續飛。處理資源時依照[Three.js清理規則](https://threejs.org/manual/pages/cleanup.html)保留所有仍被使用的共享資源。

## 6. 分期、檔案範圍與驗收

| 階段 | 具體交付 | 完成條件 |
|---|---|---|
| A：基準與美術定稿 | 同一飛行狀態的現況截圖；全球／40km／發射場三張風格樣稿；source資料版本 | 先確認海岸、色盤、雲形、近遠景一致性；建立真機舊版基準 |
| B：地球主體 | 全球與局部兩級色圖、新海岸mask、河流／地貌、接縫修正 | 同一地標在地面／高空／全球一致；手機正常觀看可見細節；GPU／ZIP預算內 |
| C：太空與雲 | 雲帶、大氣參數、星等分佈、淡星野背景 | 轉鏡不穿地球、不遮軌道；天空隨高度自然過渡；穩態幀時間過關 |
| D：近景統一 | 火箭atlas、發射場配色、地面材質和必要LOD調整 | 裝配／飛行可辨識，實例數和draw calls不超限；不重做已有正常分離邏輯 |
| E：效能收尾 | 按量測結果減少暫停工作、必要畫質降級、完整本地包 | 真機10分鐘飛行與轉鏡，無持續惡化；source／ZIP回歸、故障與恢復過關 |

先做B的全球地球與局部海岸，因為這是目前最明顯、視覺收益最高的問題；星雲、城市燈光、體積雲等不列入首輪。

主要修改scene-art.js（資產、材質、地理）、scene.js（星空、光照、LOD）；只有量測必要才動main.js（重畫排程）。新增資產必須同步manifest；只改美術時不改model／orbit／scoring／persistence。擴充tools/rocket-space-mission-browser-regression.js，沿用test-registry已登記owner；新增獨立工具／測試時才新增registry條目。

驗證場景：高度0、1、5、20、40、60、100、940.4km；跟隨／全景／軌道、正反面、極區、跨經線接縫、極端zoom；手機320×568、375×600、390×664、390×844、844×390、短iframe390×460，以及桌面。截圖必須以相同鏡頭／狀態前後比較並目視，不只驗像素數或三角形。

現有artBenchmark只迴圈28幀並略過前幾幀，適合快速冒煙檢查，不能證明持續性能；本輪美術實作時應擴充此既有案例。性能每機先暖機10秒，記錄60秒固定輸入軌跡，再持續操作10分鐘；各新舊版本至少三次，記錄機型、OS、瀏覽器、DPR、發熱、幀間隔及輸入延遲。Chrome軟體GPU回歸只驗正確性和資源上限，不能當作iPhone性能結果。最低包含一部仍支援目標Safari的較舊iPhone、一部近年iPhone和一部中階Android；型號按實際可借裝置記錄。

手機普通Safari須驗工具列展開／收起、直橫轉向、數字鍵盤顯示／關閉、安全區與最後控制可達。100dvh會隨動態viewport調整，仍需實機驗證工具列和鍵盤行為。[WebKit說明](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/)。另外保留trusted touch、fullscreen不支援訊息、部分提交、Moodle續做、pending／review鎖定、context loss與資源重複建立檢查；不把本地通過稱作Moodle-ready。

## 7. 設計決定（P27）

先交付可用的普通手機面板；後續採用「簡化真實輪廓＋卡通手繪色圖＋少量3D近景」主方案。第一輪美術重點是地球和局部海岸，之後雲與星空，最後統一近景。性能以貼圖記憶體、每幀成本及真機長時間測量一同把關，未量測前不承諾零性能損失。


## 8. P28實作與驗收

已採用Natural Earth的land／lakes／rivers向量，在離線製作工具烘焙成卡通圖層；全球與局部共用經微調的海岸，保留島群、河流、淺海色帶、植被與山脊明暗。手機2K、桌面4K全球圖二選一；局部2K、雲1K、低對比星野1K。五張圖片646,460 bytes，地理資料34,694 bytes，來源版本、SHA-256、固定seed及離線重建方法見[素材說明](../tools/rocket-art/README.md)。沒有新增瀏覽器依賴。

雲層改用相同的經緯度方向取樣，星空以方向固定的球面背景和1,050個不同大小／亮度的星點呈現；背景沿用球體UV，避免每像素再算atan／asin；保留地球遮擋、淡入及模型時間控制。近景保留既有低面數／實例化幾何，統一火箭材質明暗、河道與山脊位置，樹木避開近台河岸及道路。

渲染層移除HUD更新幀的重複draw，軌道路徑在該次draw前更新；暫停時不逐幀重算DOM操作位置。載圖失敗仍保留紀錄與提交路徑。運行時略過首2秒，以120個有效frame interval的p90超過40ms觸發降級、每級冷卻5秒；DPR桌面2→1.5→1.25，手機1.5→1.25→1，最低級隱藏微小鉚釘與近地裝飾。暫停重設採樣，不自動升級，不改物理精度、HTML文字、命中區、雲或教學疊圖。

可列舉貼圖連mipmap估算為手機45.6MiB、桌面84.6MiB，均在預算內；不包括framebuffer／MSAA／driver記憶體。這是尺寸估算，非完整GPU記憶體量測。既有browser owner的artBenchmark改為每尺寸四個固定場景各暖機2.5秒＋採樣15秒（合計10秒暖機、60秒採樣），記錄p50／p95和樣本數。Chrome SwiftShader用來對比同機成本及驗證資源上限，不用來宣稱iPhone達到30fps。

七個活動Node測試（包含新art.test.js）、靜態及manifest檢查、test registry（279 entries）已通過。完整source／extracted ZIP結果、基準對比與發布識別碼記在[活動計劃P28](../plans/40-rocket-space-mission-lab.md)。舊版基準保存在output/rocket-art-baseline-20261025，原始報告及截圖在output/playwright/rocket-space-mission-lab。

仍須在真iPhone／Android做Safari動態工具列、鍵盤、安全區、網路冷載、三輪60秒路徑及10分鐘熱負荷測量；本地無該硬件，不能把Chrome手機尺寸模擬當作真機驗收。真Moodle與獨立宿主矩陣亦未在本輪執行。


本機對比的補充限制：最終手機發射台三輪source採樣有一次p95=50ms，其餘兩次及三次package均33.5ms；舊版三次33.5ms。已降低背景逐像素計算，但仍保留首次入景慢幀觀察，不宣稱每個初次入景樣本都符合10%回退門檻。完整原始證據與最後runtime hash見P28。
